# Hamtayar UI Constitution

قانون اساسی توسعه فرانت‌اند و رابط کاربری آزمایشی همتایار

## دامنه و مرجع اجرا

این سند فقط بر پروژه `hamtayar-ui` حاکم است. هدف فعلی، ساخت رابطی فارسی، قابل نمایش،
قابل تست و قابل ارتقا برای سه فضای کاری اسناد، پرسش‌وپاسخ و کدبیس است.

محدوده مجاز شامل صفحات، اجزای رابط، routing، state، فرم‌ها، تنظیمات مرورگر، fixtureها،
clientهای HTTP، تست‌ها و ابزارهای build فرانت‌اند است. تغییر کد سرویس‌های دیگر، ساخت API،
تغییر دیتابیس یا پیاده‌سازی workflow در این محدوده نیست؛ حتی تغییر کوچک سرویس بیرونی
باید به کار جداگانه ارجاع شود. خواندن قرارداد عمومی برای ساخت client مجاز است.

ریشه پروژه `Hamtayar/hamtayar-ui` و مسیر مرجع این سند
`.specify/memory/constitution.md` داخل همین پروژه است. اسناد Spec Kit این UI باید
یک مالک و یک نسخه فعال داشته باشند و در پروژه‌های دیگر تکثیر نشوند.

MUST یعنی الزام، MUST NOT یعنی ممنوعیت، SHOULD یعنی توصیه با امکان عدول مستند و
MAY یعنی اختیار در محدوده تعیین‌شده.

## Core Principles

### I. محدوده کوچک، ساختار روشن و کد قابل نگهداری

- هر تغییر MUST یک نیازمندی یا ایراد قابل ردیابی را حل کند؛ قابلیت‌های آینده MUST NOT
  صرفاً برای «آماده‌سازی معماری» ساخته شوند.
- نام‌های کد MUST انگلیسی، معنادار و مطابق قراردادهای TypeScript/React پروژه باشند.
- component، hook و service MUST مسئولیت روشن داشته باشند. اندازه فایل به‌تنهایی
  معیار شکستن آن نیست؛ جداسازی MUST بر اساس مسئولیت یا نیاز واقعی استفاده مجدد باشد.
- abstraction و dependency جدید MUST دلیل عملی داشته باشند. استفاده مجدد SHOULD
  تکرار معنادار را حذف کند و MUST NOT به ساخت framework داخلی تبدیل شود.
- کد بلااستفاده، TODO مبهم و پیاده‌سازی موازی قابلیت موجود MUST NOT بخشی از تحویل نهایی باشند.
  کار عقب‌افتاده MUST در tasks یا مستند محدودیت‌ها با علت ثبت شود.

دلیل: این UI باید سریع قابل فهم و اصلاح باشد و هزینه نگهداری آن از مسئله بزرگ‌تر نشود.

### II. مرزبندی اجزای فرانت‌اند

- pageها MUST مسئول چیدمان و هماهنگی تعامل باشند؛ جزئیات HTTP، serialization و
  localStorage MUST در آنها پراکنده نشود.
- componentهای عمومی MUST مستقل از endpoint و نام سرویس باشند و ورودی/رویداد مشخص بگیرند.
- فراخوانی API MUST از client مشترک و adapter قابلیت مربوط عبور کند.
- منطق فرم متادیتا MUST مشترک باشد تا فرم سند، اطلاعات کاربر و فیلترها رفتار سازگار داشته باشند.
- fixtureهای Demo MUST از adapterهای API جدا باشند؛ page نباید دو نسخه مستقل از UI داشته باشد.
- ماژول‌های مشترک MUST به pageهای مشخص وابسته نشوند. وابستگی حلقوی MUST NOT ایجاد شود.
- `authService` و `metadataConfigService` MUST مرز ساده و قابل تعویض داشته باشند؛
  جایگزینی آینده آنها SHOULD بدون بازنویسی pageها ممکن باشد.

ساختار اولیه SHOULD ساده و متناسب با تعداد فایل‌ها باشد: `app` یا `pages`، `components`،
`services`، `config`، `types` و `fixtures`. ساخت پوشه‌های خالی و سلسله‌مراتب اضافی الزامی نیست.

### III. TypeScript و قرارداد داده

- پروژه جدید MUST از React، TypeScript و Vite مطابق plan استفاده کند؛ اگر UI سازگار موجود
  است، بازنویسی آن صرفاً برای تطبیق نام ابزار مجاز نیست.
- TypeScript MUST در حالت strict استفاده شود. `any`، cast اجباری یا suppression
  MUST NOT خطای واقعی قرارداد را پنهان کند؛ استثنا باید محدود و دارای دلیل باشد.
- مدل فرم، مدل داخلی UI و DTO ارتباط HTTP MUST در صورت تفاوت از هم جدا شوند و mapping
  صریح داشته باشند. تغییر label فارسی MUST نام کلید ارسالی API را تغییر ندهد.
- پاسخ شبکه و داده خوانده‌شده از مرورگر MUST ورودی نامطمئن تلقی شوند؛ شکل موردنیاز
  MUST پیش از مصرف بررسی شود. type annotation به‌تنهایی اعتبارسنجی runtime نیست.
- خطای parse یا ناسازگاری پاسخ MUST به خطای قابل فهم تبدیل شود؛ مقدار ناقص MUST NOT
  با داده ساختگی جایگزین شود و موفق معرفی شود.
- نوع‌های مشترک MUST یک مالک مشخص داشته باشند؛ کپی آنها در چند page ممنوع است.

### IV. زبان بصری منسجم و تجربه فارسی

- رابط MUST فارسی و RTL باشد. JSON، code، path، identifier و URL MUST در ناحیه مناسب
  LTR نمایش داده شوند، بدون برهم زدن ترتیب متن فارسی اطراف.
- رنگ، فاصله، typography، radius و حالت‌های تعاملی SHOULD از مجموعه کوچک tokenهای مشترک
  بیایند. button، input، alert، badge و card MUST در صفحات رفتار و ظاهر سازگار داشته باشند.
- رنگ‌بندی مرحله فعلی SHOULD روشن با آبی/سرمه‌ای باشد؛ افزودن themeهای متعدد نیاز فعلی نیست.
- CSS SHOULD از ویژگی‌های منطقی مانند inline-start استفاده کند؛ اصلاح پراکنده RTL با
  offsetهای ثابت MUST NOT جای چیدمان درست را بگیرد.
- متن‌ها MUST کوتاه و روشن باشند؛ اصطلاحات فنی و payload خام در پنل اختیاری جزئیات تست
  قرار گیرند، نه در مسیر اصلی کاربر.
- loading، empty، success، error و unavailable MUST از هم قابل تشخیص باشند.
- نام طولانی فایل، پاسخ چندخطی و فهرست بزرگ‌تر از صفحه MUST چیدمان را نشکنند.
- UI MUST در اندازه 1366×768 بدون scroll افقی کل صفحه قابل استفاده باشد؛ در عرض 390px
  نیز navigation و actionهای اصلی در دسترس بمانند. پنل کد MAY scroll داخلی داشته باشد.

### V. دسترس‌پذیری و رفتار قابل پیش‌بینی

- عناصر تعاملی MUST با HTML معنایی مناسب ساخته شوند؛ div کلیک‌پذیر MUST NOT جای button
  یا link را بدون دلیل و رفتار دسترس‌پذیر بگیرد.
- inputها MUST label داشته باشند؛ خطای فیلد MUST به همان کنترل مرتبط و قابل مشاهده باشد.
- عملیات اصلی MUST با keyboard قابل اجرا باشند و focus MUST قابل مشاهده باقی بماند.
- dialog MUST مدیریت focus، خروج مناسب و بازگرداندن focus به کنترل آغازگر داشته باشد.
- وضعیت MUST NOT فقط با رنگ نشان داده شود؛ متن یا نشانه قابل فهم نیز لازم است.
- پیام تغییر وضعیت مهم SHOULD برای فناوری کمکی قابل اعلان باشد، بدون اعلان‌های تکراری و مزاحم.
- animation MUST ضروری و محدود باشد و ترجیح reduced motion کاربر رعایت شود.
- action غیرفعال MUST دلیل قابل فهم داشته باشد. حذف داده واردشده MUST با اطلاع کاربر انجام شود.

### VI. مالکیت state و چرخه عمر تعامل

- هر داده MUST یک منبع اصلی حقیقت داشته باشد؛ state مشتق‌شدنی SHOULD از داده اصلی
  محاسبه شود و MUST NOT بی‌دلیل در چند محل همگام‌سازی شود.
- state محلی فرم SHOULD نزدیک فرم بماند؛ state سراسری فقط برای نیاز مشترک واقعی مانند
  session نمایشی، mode و تنظیمات مشترک استفاده شود.
- state رابط، داده پاسخ سرویس، draft فرم و داده persistent MUST از هم قابل تشخیص باشند.
- نتیجه درخواست قدیمی MUST NOT پاسخ درخواست جدیدتر را overwrite کند؛ هر عملیات
  MUST هویت و چرخه عمر مشخص داشته باشد.
- هنگام unmount، تعویض مسیر یا خروج، timer، listener، polling و object URLهای موقت
  MUST پاک‌سازی شوند. response دیررس MUST نشست بعدی را تغییر ندهد.
- logout MUST session و نتایج/اطلاعات موقت کاربر را پاک کند؛ تعریف فیلدهای غیرحساس MAY باقی بماند.
- اعتبارسنجی یا شکست شبکه MUST NOT بدون ضرورت ورودی کاربر را پاک کند.

### VII. فرم‌های dynamic و تنظیمات محلی

- فیلدها MUST از تعریف قابل ویرایش تولید شوند؛ تغییر تعریف MUST بدون تغییر component
  در فرم مربوط منعکس شود.
- تعریف فیلد MUST حداقل key پایدار، label فارسی، scope، type، required، enabled، visibility
  و options لازم را داشته باشد؛ فیلترها از فیلدهای سندِ filterable مشتق شوند.
- `text`، `number`، `boolean`، `select` و `multi_select` MUST طبق PRD پشتیبانی شوند.
- key تکراری، option نامعتبر و مقدار ناسازگار MUST رد شوند. `0` و `false` مقدار خالی نیستند؛
  unset با false باید قابل تفکیک باشد.
- required بودن متادیتای سند MUST NOT فیلتر همان فیلد را در پرسش اجباری کند.
- فیلد غیرفعال/پنهان و option حذف‌شده MUST NOT مقدار قدیمی را مخفیانه به request اضافه کنند.
- تغییر type یا حذف فیلد که داده draft را از بین می‌برد MUST پیش از اجرا به کاربر اعلام شود.
- اطلاعات توصیفی کاربر MUST صرفاً داده دستی تلقی شود. کلیدهای امنیتی و فیلدهای ثابت
  سیستم MUST در فهرست رزرو باشند و از متادیتای سفارشی جدا بمانند.
- فقط تعریف فیلدها و تنظیمات غیرحساس لازم MAY در localStorage ذخیره شوند؛ نام کلیدها
  MUST namespace اختصاصی UI داشته باشد تا داده سایر برنامه‌ها پاک نشود.
- داده ذخیره‌شده MUST هنگام خواندن اعتبارسنجی شود. خرابی، نبود storage یا خطای quota
  MUST قابل مشاهده باشد و MAY با حالت موقت in-memory ادامه یابد؛ ادعای ذخیره موفق ممنوع است.
- restore defaults MUST فقط تنظیمات متعلق به این UI را تغییر دهد و اثرش بر draftها را روشن کند.
- محتوای فایل، پاسخ‌ها، credential واقعی و اطلاعات حساس MUST NOT پیش‌فرض persist شوند.

### VIII. ورود هاردکد، فقط برای دمو

- حساب `demo` با رمز `Hamtayar123!` MAY در فایل config دمو قرار گیرد؛ این یک استثنای
  صریح برای داده عمومی نمایشی است، نه مجوز هاردکد کردن secret.
- ورود MUST در فرانت‌اند بررسی و با برچسب «محیط آزمایشی» معرفی شود.
- session نمایشی MUST با refresh همان نشست حفظ شود و با logout پاک شود؛ sessionStorage
  برای این هدف مجاز است. خود password MUST NOT در storage یا log ثبت شود.
- routeهای داشبورد MUST این session را برای تجربه ورود بررسی کنند؛ این کنترل MUST NOT
  امنیت واقعی یا credential معتبر سرویس معرفی شود.
- secret واقعی MUST NOT در source، fixture، bundle یا متغیر محیطی قابل انتشار فرانت‌اند قرار گیرد.
- متن پاسخ و فایل انتخاب‌شده MUST داده نامطمئن تلقی شوند. Markdown MUST بدون اجرای
  HTML یا script نامطمئن render شود و لینک‌های با scheme خطرناک MUST مسدود شوند.
- logout یا تغییر حالت MUST از نمایش باقی‌مانده داده نشست قبلی جلوگیری کند.

### IX. صداقت حالت Demo و اتصال API

- برنامه MUST ابتدا در Demo قابل اجرا باشد. Demo/API MUST انتخاب صریح و دارای برچسب دائمی باشند.
- Demo MUST از fixtureهای محلیِ قابل تکرار استفاده کند و MUST NOT درخواست عملیاتی
  به سرویس خارجی ارسال کند. هر نتیجه و log نمونه MUST نمایشی بودن خود را حفظ کند.
- API mode MUST فقط نتیجه واقعی دریافت‌شده را نمایش دهد؛ fallback خودکار به Demo ممنوع است.
- تغییر mode در زمان عملیات MUST مسدود باشد؛ پس از تغییر، نتایج موقت و history حالت قبلی
  MUST پاک شوند و تنظیمات متادیتا MAY حفظ شوند.
- قرارداد سرویس MUST از مدرک معتبر مشخص شود؛ endpoint، streaming، job status، citation
  و درصد پردازش MUST NOT از ظاهر UI یا نام مسیر حدس زده شوند.
- حالت سلامت اتصال MUST از آماده بودن عملیات و موفقیت واقعی آن جدا باشد.
- client فرانت‌اند MUST از آدرس و timeout قابل تنظیم استفاده کند و headerهای حساس
  MUST در جزئیات تست یا console چاپ نشوند.
- اطلاعات واردشده و payload واقعی ارسالی MUST در صورت تفاوت به‌وضوح تفکیک شوند.
- حذف متادیتا یا فیلتر پشتیبانی‌نشده MUST انتخاب صریح کاربر باشد؛ request کاهش‌یافته
  MUST NOT نتیجه فیلترشده یا شخصی‌سازی‌شده معرفی شود.
- نبود قابلیت سرویس MUST در UI به unavailable با علت مشخص تبدیل شود؛ رفع آن با
  تغییر فایل‌های سرویس بیرونی در این پروژه مجاز نیست.

### X. آپلود، درخواست‌های غیرهم‌زمان و خطا

- هر فایل MUST شناسه draft و نتیجه مستقل داشته باشد؛ شکست یک فایل MUST موفقیت دیگری را حذف نکند.
- file picker و drag/drop MUST اعتبارسنجی یکسان نوع/حجم داشته باشند. اعتبارسنجی مرورگر
  فقط کمک UX است و MUST NOT تضمین اعتبار فایل معرفی شود.
- فایل بزرگ MUST NOT صرفاً برای preview یا log به‌طور کامل به متن/base64 در حافظه تبدیل شود.
- ارسال multipart MUST از ابزار مرورگر برای boundary استفاده کند؛ ساخت دستی ناسازگار ممنوع است.
- double submit MUST مهار شود؛ شناسه منبع در retry آگاهانه MUST بی‌دلیل تغییر نکند.
- درخواست تغییردهنده مانند upload MUST NOT خودکار retry شود؛ retry خواندنی در صورت نیاز
  MUST محدود باشد و lifecycle آن هنگام خروج/تعویض صفحه مدیریت شود.
- توقف انتظار یا Abort در مرورگر MUST NOT لغو قطعی پردازش سرویس معرفی شود.
- timeout، قطع شبکه، پاسخ نامعتبر، validation error و no_evidence MUST معانی مجزا داشته باشند.
- مقدار null MUST NOT بدون قرارداد به صفر یا رشته موفقیت تبدیل شود.
- جزئیات تست SHOULD زمان انتظار، mode، وضعیت و request_id واقعی را نشان دهد؛
  نبود request_id MUST با مقدار جعلی جبران نشود.
- خطا MUST پیام فارسی مفید داشته باشد؛ raw traceback و داده حساس MUST NOT نمایش داده شوند.

### XI. کارایی و ابزار توسعه متناسب با دمو

- تعامل محلی و ویرایش متادیتا SHOULD روی محیط آزمون مستند در کمتر از یک ثانیه بازخورد بدهند؛
  latency سرویس جدا گزارش شود و ادعای عملکرد بدون اندازه‌گیری ممنوع است.
- محاسبه سنگین، parse غیرضروری و render تکراری بزرگ MUST NOT مسیر اصلی تعامل را مسدود کنند.
- بهینه‌سازی مانند memoization و virtualization SHOULD پس از مشاهده نیاز انجام شود،
  نه به‌عنوان پیچیدگی پیش‌فرض همه componentها.
- package manager پروژه MUST مشخص و lockfile آن نگهداری شود؛ lockfileهای متعارض ممنوع‌اند.
- env نمونه MUST فقط تنظیمات غیرحساس داشته باشد؛ README MUST نسخه runtime آزموده‌شده
  و فرمان‌های نصب و اجرای PowerShell را مشخص کند.
- formatter، lint، typecheck و build MUST فرمان‌های قابل تکرار داشته باشند. خاموش کردن
  کلی کنترل کیفیت برای عبور از خطا MUST NOT انجام شود.
- کتابخانه در محدوده plan مصوب MAY با توجیه کوتاه اضافه شود؛ وابستگی خارج از آن
  یا تغییر عمده stack MUST پیش از اجرا با مالک پروژه هماهنگ شود.

### XII. تست رفتاری و شواهد قابل بازتولید

- منطق اعتبارسنجی، serialization، mapping و storage MUST با تست متناسب پوشش داده شود.
- تست component MUST رفتار کاربر را بسنجد؛ جزئیات داخلی implementation و snapshotهای
  حجیم MUST NOT جای آزمون رفتار اصلی را بگیرند.
- مسیر ورود/خروج، تغییر تنظیمات و اثر آن بر فرم، مستقل بودن فایل‌ها، ارسال سؤال، خطاها
  و جداسازی Demo/API MUST آزمون مشخص داشته باشند.
- حداقل یک مسیر کامل ورود تا اجرای عملیات نمایشی MUST بدون سرویس خارجی بررسی شود.
- تست Demo MUST نبود درخواست عملیاتی را بررسی کند؛ تست client با mock MUST آزمون
  شبکه واقعی معرفی نشود.
- stale response، دوبار کلیک، `0`/`false`، storage خراب و payload پشتیبانی‌نشده SHOULD
  در آزمون‌های مربوط پوشش داده شوند.
- RTL، keyboard، focus، عرض‌های هدف و متن/نام فایل طولانی MUST عملاً بررسی شوند.
- lint، typecheck، build و تست‌های مرتبط MUST اجرا و خروجی واقعی گزارش شود.
- تست اجرا نشده یا مسدود MUST با علت ثبت شود؛ عدد تست یا نتیجه passed ساختگی ممنوع است.
- تسکی با معیار پذیرش محقق‌نشده MUST NOT Done شود. اتصال خارجی مسدود، نقص مستقل UI را
  توجیه نمی‌کند و MUST از تکمیل دموی محلی جدا گزارش شود.

## فرایند Spec Kit و کنترل محدوده

1. **Specify:** هدف و رفتار از PRD استخراج شود؛ نسخه فعال spec متعلق به همین UI باشد.
2. **Clarify:** فقط ابهام مؤثر رفع شود؛ تصمیم‌های قطعی مانند ورود نمایشی و RTL دوباره سؤال نشوند.
3. **Plan:** ساختار، قرارداد client، state، storage، ابزارها و روش آزمون مشخص شوند.
4. **Tasks:** کارها کوچک، وابسته به نیازمندی و دارای معیار اتمام باشند.
5. **Analyze:** ناسازگاری اسناد و گسترش محدوده پیش از اجرای بخش مربوط رفع شود.
6. **Implement:** تغییرات محدود به پروژه UI و تسک جاری باشند.
7. **Verify / Deliver:** رفتار با معیار پذیرش بررسی و نتیجه واقعی مستند شود.

نام و syntax فراخوانی مراحل MUST مطابق نسخه نصب‌شده باشد. این سند الزام به نصب مجدد
یا بازنویسی تنظیمات Spec Kit ایجاد نمی‌کند. PRD مشخص می‌کند چه ساخته شود؛ constitution
قواعد ساخت را تعیین می‌کند؛ plan محل جزئیات فنی و tasks محل پیگیری اجراست.

### Constitution Check برای هر plan

| بررسی | شواهد مورد انتظار |
|---|---|
| دامنه | همه فایل‌های قابل تغییر در پروژه UI هستند؛ وابستگی خارجی فقط قرارداد client است. |
| سادگی | هر dependency یا abstraction جدید دلیل فعلی دارد. |
| UX | RTL، دسترس‌پذیری و حالت‌های loading/empty/error تعریف شده‌اند. |
| داده | مالک state، محل persistence و پاک‌سازی داده مشخص است. |
| فرم | type و required و اثر تغییر تعریف فیلد قابل آزمون است. |
| ارتباط | Demo/API، payload واقعی، خطا و timeout رفتار مشخص دارند. |
| امنیت مرورگر | secret منتشر نمی‌شود و محتوای نامطمئن امن render می‌شود. |
| آزمون | معیارهای پذیرش و فرمان‌های اعتبارسنجی به تسک‌ها متصل‌اند. |

## استفاده از ایجنت و Git

- ایجنت MUST فایل‌های مرتبط، قراردادها و تغییرات موجود را پیش از ویرایش بررسی کند.
- فایل نامرتبط یا تغییرات کاربر MUST NOT بازنویسی یا حذف شود.
- انتخاب معمول در محدوده مصوب MAY مستقل انجام شود؛ گسترش دامنه یا تغییر معماری
  MUST پیش از اجرا ثبت و هماهنگ شود.
- branch، commit، push، MR و انتشار MUST فقط مطابق مجوز و روش اعلام‌شده کاربر انجام شوند؛
  تحویل محلی MUST به انجام خودکار این عملیات وابسته نباشد.
- عملیات مخرب MUST بدون مجوز صریح انجام نشود. فایل‌های تولیدی، cache و تنظیمات شخصی
  MUST طبق قواعد پروژه از کنترل نسخه خارج بمانند؛ lockfile و اسناد مرجع نگهداری شوند.
- گزارش تحویل MUST diff/فایل‌های تغییرکرده، رفتار نهایی، تست‌ها و محدودیت‌ها را روشن کند.
- بررسی و پذیرش نهایی با انسان است؛ استفاده از AI جای شواهد را نمی‌گیرد.

## دروازه تحویل و Definition of Done

تحویل MUST شامل کد قابل اجرا، README فارسی، env نمونه، lockfile، نتایج واقعی کنترل کیفیت
و وضعیت به‌روز tasks باشد. روش ورود، تنظیمات محلی و تغییر Demo/API MUST مستند باشند.

دو نتیجه MUST جدا ثبت شوند:

- **تکمیل UI دمو:** ورود، navigation، تنظیمات متادیتا و سه فضای کاری در حالت Demo قابل استفاده‌اند.
- **وضعیت اتصال:** برای هر عملیات یکی از «متصل و آزموده»، «client آماده ولی آزمون واقعی اجرا نشده»،
  «مسدود به علت سرویس خارجی» یا «صرفاً نمایشی» ثبت شده است.

اگر سرویس خارجی آماده نیست، UI می‌تواند طبق معیارهای دمو تحویل شود؛ تکمیل اتصال واقعی
MUST NOT ادعا شود. معیارهای product/production آینده بخشی از این تحویل نیستند.

## Governance

- این سند تنها مرجع فعال قواعد `hamtayar-ui` در `.specify/memory/constitution.md` است.
- این نسخه محدوده را به فرانت‌اند محدود می‌کند. بندهای PRD قبلی که تغییر محدود سرویس را
  مجاز می‌دانند MUST در specification به کار frontend client محدود شوند؛ کار سرویس
  به‌عنوان وابستگی یا follow-up ثبت شود و مالکیت Spec Kit در UI قرار گیرد.
- تعارض واقعی MUST پیش از پیاده‌سازی بخش متعارض در spec/plan/tasks حل و ثبت شود؛
  هیچ فایل مرجعی نباید بی‌اطلاع کاربر به‌صورت گسترده بازنویسی شود.
- اصلاح constitution MUST دلیل، اثر بر اسناد فعال و پذیرش مالک پروژه داشته باشد.
- SemVer MUST رعایت شود: MAJOR برای تغییر ناسازگار اصل/دامنه، MINOR برای الزام جدید
  سازگار و PATCH برای شفاف‌سازی بدون تغییر معنا.
- استثنا MUST محدود و دارای دلیل و شرایط پایان باشد؛ استثنای فعلی فقط ورود هاردکد
  و تنظیمات محلی برای دمو است و اجازه نگهداری secret واقعی ایجاد نمی‌کند.
- برای عبور از دمو به محصول واقعی، این استثناها و معیارهای تحویل MUST بازنگری شوند.
- تاریخ تصویب MUST فقط پس از پذیرش مالک ثبت شود؛ تدوین سند به معنی تأیید رسمی تیم نیست.
